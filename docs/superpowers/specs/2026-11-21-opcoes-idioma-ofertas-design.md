# Activity options, guide-language surcharge and automatic offers (part 2 of 3)

Date: 2026-11-21. Owner: Rits Delgado.

## Intent

The owner wants the Discover booking to work like the Logan Tours site (loganislandtours.com), keeping the Discover look. Parts 1 and 3 are deployed: the complete page, the booking column, the server quote, held places and duplicates. Part 2 adds the three pricing features Logan has and SalDesk lacks.

The reference is the package `Downloads/modulo-reserva-saldesk`:
- `api/CONTRATO-API.md`, section "Regras de preço";
- `standalone/booking-widget.js`;
- `original-logan/services/Pricing.php`.

Use it as a reference for behaviour only. Do not copy its code.

**Why now:** operators already work around the missing options by duplicating activities. Zy Tours has "Buggy Zforce 1000cc – 02Hr" and "– 03Hr" as two separate activities, and "TOUR – Salinas e Baía dos Tubarões" next to "… (Privado)". A buggy is exactly Logan's "per vehicle" case.

## Owner decision (2026-11-21)

Options cover **any variation** of one activity, not only vehicles. Examples: "2 horas / 3 horas", "Manhã / Tarde", "Com almoço / Sem almoço", "Buggy 2 lugares". The owner handed the rest of the how to the builder (see "Builder calls").

## How it works today

- **Data:** activity data lives in the unit's description JSON (`meta`), edited in `frontend/src/components/units/forms/TourForm.jsx`. It covers:
  - prices: `base_price` (per person), `meta.price_child`, `meta.price_private`, `meta.price_tiers` (private price per group-size band);
  - `meta.languages` (codes such as `PT`, `EN`, `ES`, `FR`);
  - `meta.time_slots`;
  - `unit.capacity`.
- **One price function:** `precoActividade(unit, meta, { adults, children, mode })` in `backend/src/helpers/bookingHelpers.js`. Both the quote (`GET /public/:slug/units/:id/quote`) and the booking POST (`criarReserva`) use it, and a test pins them together. Vouchers (discount codes) are applied after it, in `criarReserva` and `cotarActividade`. A code is used up on payment for card bookings (part 3).
- **Booking column:** `frontend/src/components/servico/ReservaActividade.jsx`. Its steps:
  1. a per-person / private toggle, when both exist;
  2. who's coming, plus the guide-language select;
  3. calendar and slots;
  4. a price box built from the server's quote lines, with the voucher field.

  The quote already has a `before` field, always `null` today.
- **Booking modal:** the modal in `frontend/src/pages/ServiceDetail.jsx` (`ActivityModal`, `col` selection) posts the selection. The guide language goes into the booking notes (`Idioma: …`).
- **"Desde" price:** the Discover card's price (`website/discover/_cartao.js` `precoCartao`) and the server's `displayPrice` (`backend/src/controllers/catalogImageController.js`) use `base_price`, else the cheapest tier, else the private price.
- **Discounts:** the only discounts are voucher codes (table `vouchers`). There are no automatic offers.

## Goals

### 1. Options (variants)

An activity may have a list of options. Each option has:
- `id`: stable, generated by the form;
- `name_pt` and `name_en` (EN optional; falls back to PT);
- `type`:
  - `per_person`: (adults × price) + (children × child price, or the price when no child price is set);
  - `per_group`: one price for the whole booking;
  - `per_vehicle`: vehicles × price;
- `price` (> 0);
- `price_child`: optional, used by `per_person` only;
- `seats`: required for `per_vehicle`, an integer ≥ 1. It is the number of seats per vehicle.

How options behave:
- **They replace the price table.** When an activity has options, the public page and the price ignore `base_price`, `price_child`, `price_private` and `price_tiers`, and the per-person / private toggle disappears. Without options, everything stays exactly as today.
- **Choosing:** the column's first step becomes "Opção". It lists each option with its price and unit ("por pessoa", "por grupo", "por veículo (N lugares)"). The first option is pre-selected.
- **Vehicles:** with a `per_vehicle` option, a "Veículos" counter appears.
  - The minimum is ⌈people ÷ seats⌉. The maximum is people (one person per vehicle).
  - The counter follows the people count and stays within those limits.
  - The server recomputes the vehicle count within the same limits and never trusts the browser.
- **Capacity and calendar:** options share the activity's capacity (`unit.capacity`), time slots, blocked days and booked places.
  - A `per_group` option takes the whole slot or day exclusively, like today's private mode.
  - `per_person` and `per_vehicle` count people against the shared capacity.
  - Day and slot availability for a `per_group` option uses today's private rules.
- **The booking stores** the chosen option and the vehicle count in its notes, so the operator sees them: `Opção: <nome>`, and `Veículos: N` when relevant. The guide language is already stored there.

### 2. Guide-language surcharge

- **Setting it:** for each language the activity offers, the operator may set a surcharge in the activity form: a fixed amount per booking, where 0 or empty means none. It is stored as `meta.language_surcharges`, e.g. `{ "ES": 20 }`.
- **Pricing:** the chosen guide language's surcharge becomes a quote line of type `language`: "Suplemento de idioma (Español)" / "Language surcharge (Spanish)". It applies with or without options.
- **The select:** the guide-language select shows the surcharge next to the language, e.g. "Español (+20 €)".
- **When the select is shown:** today it appears only when the activity has more than one language. It now also appears when the only language has a surcharge, so the price is never hidden.

### 3. Automatic offers

- **Setting them:** the operator may add offers to an activity, stored as `meta.offers`, a list. Each offer has:
  - `percent`: an integer from 1 to 90;
  - `from` and `to`: travel dates, inclusive, `YYYY-MM-DD`;
  - an optional label, PT and EN, e.g. "Oferta de época baixa".
- **When an offer applies:** when the chosen date falls within its dates. With several matching offers, the highest percent wins.
- **Codes:** offers and voucher codes never add up. When both are present, the one giving the bigger discount wins.
- **What the discount applies to:** the total, including the language surcharge.
- **Quote:**
  - the discount is a line of type `discount`, for example "Oferta especial (-25%)", or the offer's label;
  - `before` carries the total before the discount;
  - the price box shows it struck through next to the new total.
- **The column header:**
  - shows a small badge, for example "-25% de 1 a 15 dez", when the activity has an offer whose `to` is today or later (Cape Verde time);
  - when several offers are current, shows the one ending first;
  - the struck price appears only once a date is chosen, because offers depend on the date.

### 4. One price function, extended

- **Signature:** `precoActividade` becomes `precoActividade(unit, meta, { adults, children, mode, optionId, vehicles, guideLanguage, date })` and returns `{ total, lines, before, error }`.
- **Same function everywhere:** the quote and `criarReserva` both call it, and vouchers are compared inside the same flow.
- **Errors:**
  - a missing or unknown option when the activity has options: `OPTION_REQUIRED`, "Escolha uma opção" / "Choose an option";
  - the existing `CAPACITY_EXCEEDED`, `MIN_ADULTS` and private-band errors keep working.
- **Request fields:**
  - the quote takes `option`, `vehicles` and `glang` query parameters;
  - the booking POST takes `option_id`, `vehicles` and `guide_language`;
  - all are optional, so older pages and the widget keep working when the activity has no options.
- **Test:** the test that pins the quote to the charged amount is extended to cover options, surcharge, offer and voucher.

### 4b. Operator and beach-seller bookings (owner answer, 2026-11-21)

The screens where the operator or a beach seller creates an activity booking get the same option choice, plus the vehicle counter for a `per_vehicle` option, whenever the activity has options. Those screens are the panel's reservation form (including from the calendar), `BeachSale.jsx` and `BeachSeller.jsx`.

- **Price:** comes from `precoActividade` with the chosen option.
- **No option sent** (an older client): the server prices the booking with the cheapest option instead of refusing. Operator bookings are never refused (ruling R1 from part 1).
- **Notes:** the option and vehicles go into the booking notes as on the public page.
- **Not on these screens:** the language surcharge and offers do not apply. These bookings never had offers, and the operator sets the language by hand.

### 5. "Desde" price with options

The Discover card (`precoCartao`) and the server's `displayPrice` use the cheapest option's price when an activity has options. The unit is "pessoa", "grupo" or "veículo". Offers are not shown on the Discover cards in this part.

### 6. Activity form

Three new sections in `TourForm.jsx`. Each is optional and saved into `meta`. There is no database migration.

- **"Opções":** rows with name PT, name EN, type, price, child price (only for per person), and seats (only for per vehicle). Rows can be added and removed. When at least one option exists, a short note explains that the options replace the price table on the public page.
- **"Suplemento por idioma":** one amount field next to each selected language.
- **"Ofertas":** rows with percent, from, to and label PT/EN. Rows can be added and removed.

Validation:
- price > 0;
- seats ≥ 1 for per vehicle;
- percent from 1 to 90;
- `from` ≤ `to`;
- the form refuses to save invalid rows, with the error shown on the row.

## Non-goals

- Merging the operators' existing duplicated activities. The operator can do it by hand once options exist.
- Infants (Logan has them; SalDesk has none in its data).
- Offers or options on hotels, cars and restaurants.
- Showing offers on Discover cards.
- Options or offers in OTA channel sync (GetYourGuide, Viator).

## Anti-goals

- **A price on the page different from the amount charged.** One function and a test pin them.
- **Breaking today's activities without options,** older cached pages, the widget, or the part 1 and part 3 behaviour: held places, deferred notices, duplicates and vouchers.
- **Invented content:** no fake offers. The badge shows only real current offers.
- **Stacking discounts** (offer plus code).
- **Horizontal scroll at 375 px.**

## Constraints

- **App:**
  - React 18, Tailwind and vitest; `components/ui/*` never changes.
  - PT and EN through the page's `lang`.
  - Operator form strings use the i18n files `pt/en/de/nl` with the parity test.
  - European Portuguese with accents; no emojis.
- **Backend:** Express and jest. Never start the real backend in development. No migration.
- **Prices** are in the operator's currency, as today. CVE operators are converted for display exactly as today.
- **Cape Verde time** (`Atlantic/Cape_Verde`) for "today" and for offer dates.
- **Tests:**
  - jest for `precoActividade`:
    - each option type;
    - vehicle limits;
    - the surcharge;
    - offers: in range, out of range, best of several, best of offer and code;
    - `before`;
    - `OPTION_REQUIRED`;
  - jest for the quote-equals-charge pin and for `criarReserva` with the new fields;
  - vitest for the column (option step, vehicle counter, surcharge label, struck price, offer badge) and for the form sections;
  - a browser check at 375 and 1280.
- **Deploy:** the usual backups; backend before the app. The Discover site (`_cartao.js`) is deployed after the backend.

## Approaches considered

- **(a) Options in the activity's description JSON, priced by the shared `precoActividade` (chosen).** No migration, one price function, and it follows how every other activity setting is stored today.
- **(b) A separate `unit_options` table.** Rejected for now. It needs a migration, new endpoints and a new editor path, and gives nothing the JSON does not at this scale. It can be revisited if OTA sync ever needs options.
- **(c) Keep duplicated activities and group them visually on the page.** Rejected. It does not give Logan's behaviour (one activity, one calendar, shared capacity), and the operator keeps double maintenance.

## Builder calls (made by me, the owner can overrule)

- Options share the activity's capacity, slots and days. `per_group` behaves as today's private mode (exclusive).
- An option replaces the whole price table. There is no mixing of the per-person/private toggle and options.
- Children pay the option's child price when one is set, otherwise the option price (`per_person` only). For `per_group` and `per_vehicle` they only count as people.
- The language surcharge is per booking, not per person, as in Logan.
- Offers by travel date only, as in Logan (no booking-date window, no minimum group).
- The best of offer and code wins, never both. The discount applies to the total including the surcharge.
- Option, vehicles and language are stored in the booking notes, so there is no migration.

## Builder-check rulings (2026-11-21, my calls)

These answer the independent builder check.

1. **`base_price` follows the options.** When an activity has options, the form writes the cheapest option's price into `base_price`. Every existing "desde" reader then keeps working without changes:
   - `seo.js` `unitDisplayPrice`;
   - the cheapest price per operator in the Discover list;
   - `PublicBooking.jsx`;
   - related services;
   - OTA sync.

   `precoCartao` and `displayPrice` still learn the option's unit ("pessoa", "grupo" or "veículo"). The column checks for options before its per-person / private / no-price branches. Options replace the table on the public page, so the stored `base_price` is never used to price a booking that has options.
2. **Guide language and the surcharge:**
   - "Sem preferência" stays allowed and is free.
   - A surcharge is charged only when a language with a surcharge is chosen.
   - When the activity offers exactly one language and that language has a surcharge, the select has no "Sem preferência", and the server defaults `guideLanguage` to that language in both the quote and the POST. The two can never differ.
   - A code the activity does not offer is treated as "no preference" (no surcharge, no error).
3. **The option is part of "the same booking".** The duplicate check (`classificarRecentes`) also compares the chosen option, read from the booking's `Opção:` notes line, which the server writes. Two bookings with different options are never merged.
4. **A code that loses to an offer:**
   - The quote keeps the offer's discount line and adds `voucher_ignored: true`, with the message "Já existe uma oferta melhor; o código não foi aplicado" / "A better offer already applies; the code was not used".
   - The POST then ignores the code entirely: no 400 if it has run out, no `voucher_id`, no use recorded.
   - Discount lines carry `source: 'offer' | 'voucher'`. The modal forwards `voucher_code` only when the winning line's source is `voucher`, and the line text uses the offer label or "Código X" accordingly.
5. **`before`:** the struck price shows for any discount, offer or code, as the quote already sets `before` for codes today.
6. **Date:** the quote gains a `date` parameter (offers depend on it). Without a date, no offer applies.
